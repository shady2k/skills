# Keeping work

Part of the set's protocol, whose core is `protocol.md`: the same in every
project, and it wins over a project's restatement.
What is tracked, what a session may not keep only to itself, where exploration
ends and a commitment starts, and the lessons that outlive the work.

**Tracked work.** Before implementing or changing the repository, find or file
the task. Every commit names one or more existing leaf tasks by the project's
convention, including research, documentation, prototypes and setup; initial
setup files its own task before any gate exists. Read-only discussion needs no
issue until it produces work to keep. Where the project has no backlog
integration yet, work stays read-only or in scratch space, and keeping files or
commits waits for setup, which the user is asked to run. The commit check
verifies links; a clean backlog does not.

**Nothing of value stays only in this session.** A conversation is the one
place work cannot be recovered from: its files are uncommitted, what it found
is unfiled, and what it learned is in nobody's memory but the agent's. Version
control's status is the test of that, and it is read rather than recalled. When
a piece of work ends, and always before offering to stop, hand over, compact or
start a fresh session, name what this session changed that no commit holds,
which task each change belongs to, and what would carry it; where there is no
task, filing one is the next step offered, as **Tracked work** says. What the
session learned and has nowhere else to live goes through `handoff` the same
way. Say each thing once, not in every message: this is a duty to leave nothing
behind, not a checklist to recite. A session that changed files and ended with
none of it said has lost the work, whatever stopped it.

**Exploration is not admission.** Discussion, imagination and read-only
research may end with no result, task or document. A hypothesis is not an
approved requirement, a scratch experiment does not authorize production use,
and interest in an idea is not a start of work. Product and feature gates start
at the commitment to keep an implementation, not at thinking.

**A lesson that outlives the work is kept where every agent reads.** This is
the lessons-learned half of a retrospective. A trap met in this work that would
cost time again in other work goes into the project's agent doc, one line each;
a trap only this work could meet ends with it. Lessons are proposed to the user
when there are some and never asked for as a ritual when there are none, and
they land with the user's agreement in a change that tracked work carries, or
are left for the next session to land. A harness's own memory may keep them
too, but the agent doc is what every agent reads. A lesson whose cause is
removed goes in the same change that removes it.
